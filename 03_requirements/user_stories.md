# User Stories

Функция: «Управление квотами и тарифными планами отельера». Формат: «Как *<роль>*, я хочу *<действие>*, чтобы *<цель>*».
Критерии приёмки (AC) записаны на Gherkin (русская локализация). Коды `BR-xx` - бизнес-правила из [process_description.md](../02_business_process/process_description.md); `BG-x` - цели из [business_goals.md](../01_business_context/business_goals.md); `C-xx` - ограничения из [constraints.md](constraints.md).

| ID | Роль | Кратко | Приоритет (MoSCoW) |
|---|---|---|---|
| US-01 | Отельер | Задать квоту на период | Must |
| US-02 | Отельер | Создать и изменить тарифный план | Must |
| US-03 | Отельер | Экстренно закрыть продажи | Must |
| US-04 | Менеджер ТО | Согласовать или отклонить значимое изменение | Must |
| US-05 | Revenue Manager | Настроить наценки и пороги автосогласования | Should |
| US-06 | Менеджер ТО | Получать уведомления о sell-through и релиз-датах | Should |
| US-07 | Администратор системы | Мониторить публикацию и повторять её при сбоях | Must |
| US-08 | Отельер (PMS / channel manager) | Обновлять квоты и тарифы по API | Should |

## US-01. Задание квоты

> **Как** отельер, **я хочу** задать квоту номеров на период с указанием типа и релиз-периода, **чтобы** туроператор мог продавать мои номера без ручной переписки и возвращать мне невостребованные номера в срок.

**Приоритет:** Must. **Связи:** BG-1, BG-4; BR-02...BR-05; C-01, C-04.

**Acceptance Criteria**

```gherkin
# language: ru
Функция: Задание квоты отельером

  Сценарий: Успешное создание аллотмента
    Дано отельер авторизован и объект допущен к продажам
    И номерной фонд категории "Стандарт" равен 20 номерам
    Когда отельер создаёт квоту типа "Аллотмент" на 10 номеров на период с 01.07.2027 по 31.07.2027 с релиз-периодом 14 дней
    Тогда система сохраняет версию квоты со статусом "Применено"
    И инвентарь на каждую ночь периода равен 10
    И в журнале аудита создана запись с автором, временем и источником "extranet"

  Сценарий: Квота превышает номерной фонд
    Дано номерной фонд категории "Стандарт" равен 20 номерам
    И на 15.07.2027 уже действуют квоты других каналов на 15 номеров
    Когда отельер создаёт квоту на 10 номеров на 15.07.2027
    Тогда система отклоняет запись с кодом ошибки "BR-03"
    И сообщает допустимый максимум 5 номеров на эту дату

  Сценарий: Уменьшение квоты ниже проданного
    Дано на 10.08.2027 по квоте продано 7 номеров
    Когда отельер уменьшает квоту на 10.08.2027 до 5 номеров
    Тогда система отклоняет изменение с кодом "BR-04"
    И квота остаётся прежней

  Сценарий: Некорректный релиз-период
    Когда отельер указывает релиз-период 400 дней
    Тогда система отклоняет запись с кодом "BR-05" и подсказкой "допустимо 0-365"

  Сценарий: Значимое снижение квоты требует согласования
    Дано по дате остаток квоты равен 10 номерам
    Когда отельер снижает остаток до 7 номеров (на 30 %)
    Тогда версия получает статус "На согласовании" согласно "BR-10"
    И менеджеру туроператора создана задача согласования
```

## US-02. Создание и изменение тарифного плана

> **Как** отельер, **я хочу** создавать и изменять тарифные планы (цены, питание, ограничения, условия отмены), **чтобы** гибко управлять доходом и быстро выводить сезонные предложения.

**Приоритет:** Must. **Связи:** BG-1, BG-5, BG-8; BR-06...BR-09; C-02, C-16, C-17.

**Acceptance Criteria**

```gherkin
# language: ru
Функция: Управление тарифными планами

  Сценарий: Создание тарифа с питанием и ограничениями
    Дано отельер авторизован
    Когда отельер создаёт тариф "Стандарт BB" с планом питания "BB", нетто-ценой 4500 руб. за номер на период с 01.06.2027 по 31.08.2027, MinLOS 2 и политикой отмены "Стандартная"
    Тогда система сохраняет тариф как новую версию
    И новый тарифный план классифицируется как значимое изменение
    И создаётся задача согласования для менеджера

  Сценарий: Нетто-цена не положительна
    Когда отельер вводит нетто-цену 0 руб.
    Тогда система отклоняет запись с кодом "BR-06"

  Сценарий: Противоречивые ограничения проживания
    Когда отельер задаёт MinLOS 5 и MaxLOS 3
    Тогда система отклоняет запись с кодом "BR-07"

  Сценарий: Политика отмены нарушает ПП № 1912
    Когда отельер задаёт удержание 100 % предоплаты при отмене за 3 дня до заезда
    Тогда система блокирует публикацию с кодом "BR-08"
    И показывает допустимые параметры политики отмены

  Сценарий: Раскрытие скидки
    Когда отельер создаёт акцию со скидкой 15 %
    Тогда система требует указать базовую цену
    И сохраняет базовую цену и размер скидки "BR-09"

  Сценарий: Малое изменение цены применяется автоматически
    Дано действующая цена на 20.07.2027 равна 5000 руб.
    Когда отельер меняет цену на 5200 руб. (+4 %)
    Тогда изменение классифицируется как малое по "BR-10"
    И применяется без согласования, версия получает статус "Применено"

  Сценарий: Одновременное редактирование
    Дано два пользователя открыли тариф в версии 7
    Когда второй пользователь сохраняет изменения после первого
    Тогда система отклоняет сохранение с кодом "409 Conflict"
    И показывает актуальную версию 8 и различия
```

## US-03. Экстренное закрытие продаж

> **Как** отельер, **я хочу** одним действием закрыть продажи на выбранные даты и категории, **чтобы** оперативно предотвратить овербукинг при аварии, ремонте или ошибочной продаже.

**Приоритет:** Must. **Связи:** BG-2, BG-3; BR-11, BR-13; ALT-1; C-07.

**Acceptance Criteria**

```gherkin
# language: ru
Функция: Stop-sale

  Сценарий: Закрытие продаж без брони и коммитмента
    Дано объект допущен к продажам
    И на 12.09.2027 нет подтверждённых броней
    Когда отельер закрывает продажи на 12.09.2027 для категории "Стандарт" с причиной "Ремонт"
    Тогда stop-sale применяется немедленно без согласования
    И изменение опубликовано во всех каналах не позднее чем через 60 секунд (95-й процентиль)

  Сценарий: Закрытие дат с действующими бронями
    Дано на 12.09.2027 есть 3 подтверждённые брони
    Когда отельер закрывает продажи на 12.09.2027
    Тогда система показывает "затронуто броней: 3, брони не отменяются"
    И действующие брони остаются подтверждёнными
    И менеджеру создана задача "Проверить размещение гостей"

  Сценарий: Закрытие коммитментной квоты
    Дано на выбранные даты действует квота типа "Коммитмент"
    Когда отельер закрывает продажи на эти даты
    Тогда stop-sale применяется немедленно согласно "BR-11"
    И менеджеру создана задача "Оценить контрактные последствия"

  Сценарий: Обязательная причина
    Когда отельер пытается закрыть продажи без указания причины
    Тогда система не принимает запрос и требует выбрать причину

  Сценарий: Снятие закрытия
    Дано действует stop-sale на 12.09.2027
    Когда отельер открывает продажи на эту дату
    Тогда инвентарь восстанавливается до значения квоты за вычетом проданного
    И изменение публикуется в каналы
```

## US-04. Согласование значимого изменения

> **Как** менеджер туроператора, **я хочу** видеть значимые изменения в формате «было / стало» с маржой и отклонением от рыночной цены и принимать по ним решение, **чтобы** контролировать коммерческие условия, не просматривая каждую правку отеля.

**Приоритет:** Must. **Связи:** BG-1, BG-5; BR-10, BR-12; MS-9...11, ALT-2, EXC-4; C-03.

**Acceptance Criteria**

```gherkin
# language: ru
Функция: Согласование значимых изменений

  Сценарий: Согласование
    Дано создана задача согласования по тарифу "Стандарт BB"
    Когда менеджер открывает задачу
    Тогда он видит параметры "было" и "стало", изменение в процентах, расчётную маржу и отклонение от BAR
    Когда менеджер нажимает "Согласовать"
    Тогда версия получает статус "Применено"
    И запускается публикация в каналы
    И отельер получает уведомление

  Сценарий: Отклонение без причины
    Когда менеджер нажимает "Отклонить" и не заполняет причину
    Тогда система не принимает решение и требует указать причину

  Сценарий: Отклонение с причиной
    Когда менеджер отклоняет изменение с причиной "Цена выше рыночной"
    Тогда версия получает статус "Отклонена"
    И действующая версия остаётся без изменений
    И отельер получает уведомление с причиной

  Сценарий: Запрос уточнения
    Когда менеджер выбирает "Запросить уточнение" и вводит вопрос
    Тогда задача возвращается отельеру со статусом "Требуются уточнения"

  Сценарий: Нарушение SLA
    Дано задача создана в 10:00 рабочего дня
    Когда к 12:00 решение не принято
    Тогда система отправляет напоминание менеджеру и эскалирует задачу руководителю контрактинга
    И автоматического согласования не происходит

  Сценарий: Предупреждение о паритете
    Дано новая цена выше BAR более чем на 5 %
    Когда менеджер открывает задачу
    Тогда отображается предупреждение "BR-12"
```

## US-05. Настройка наценок и порогов

> **Как** Revenue Manager, **я хочу** задавать правила наценки, пороги значимости изменений и SLA согласования, **чтобы** управлять маржой и балансом между скоростью и контролем без обращения к разработчикам.

**Приоритет:** Should. **Связи:** BG-1, BG-5, BG-8; BR-10, BR-12; C-15.

**Acceptance Criteria**

```gherkin
# language: ru
Функция: Настройка правил ценообразования и порогов

  Сценарий: Задание наценки по периоду и каналу
    Дано пользователь имеет роль "Revenue Manager"
    Когда он задаёт наценку 12 % для канала "B2C" на период 01.06.2027-31.08.2027
    Тогда новая наценка применяется к расчёту продажных цен, начиная с даты "effective-from"
    И правило сохраняется как версия с записью в журнале аудита

  Сценарий: Изменение порога значимости
    Когда Revenue Manager меняет порог изменения цены с 10 % до 15 %
    Тогда новые изменения классифицируются по порогу 15 %
    И ранее созданные задачи согласования не пересчитываются

  Сценарий: Недопустимое значение
    Когда Revenue Manager вводит порог 150 %
    Тогда система отклоняет значение и требует число от 0 до 100

  Сценарий: Запрет изменения правил другими ролями
    Дано пользователь имеет роль "Менеджер ТО"
    Когда он пытается изменить пороги значимости
    Тогда система возвращает отказ в доступе "403 Forbidden"

  Сценарий: Пересчёт цен после изменения наценки
    Когда наценка изменена и сохранена
    Тогда система пересчитывает продажные цены на будущие даты и ставит публикацию в очередь
```

## US-06. Уведомления о sell-through и релиз-датах

> **Как** менеджер туроператора, **я хочу** получать уведомления при высоком расходе квоты и при приближении релиз-даты, **чтобы** вовремя докупить номера, перераспределить спрос или вернуть невостребованный остаток.

**Приоритет:** Should. **Связи:** BG-3, BG-4; BR-05; MS-16; C-13.

**Acceptance Criteria**

```gherkin
# language: ru
Функция: Мониторинг квот

  Сценарий: Уведомление о высоком sell-through
    Дано по квоте на 20.08.2027 выделено 10 номеров
    Когда продано 8 номеров (80 %)
    Тогда менеджер получает уведомление "Sell-through достиг 80 %" не позднее чем через 5 минут

  Сценарий: Напоминание о релиз-дате
    Дано релиз-период квоты равен 14 дням и дата заезда 20.08.2027
    И релиз-дата равна 06.08.2027
    Когда наступает 30.07.2027 (за 7 дней до релиз-даты)
    Тогда менеджер получает напоминание с остатком непроданных номеров

  Сценарий: Автоматический возврат остатка по релиз-дате
    Дано квота типа "Аллотмент" имеет остаток 4 номера
    Когда наступает релиз-дата
    Тогда остаток возвращается отелю
    И инвентарь туроператора уменьшается на 4
    И изменение публикуется в каналы

  Сценарий: Коммитмент не возвращается
    Дано квота типа "Коммитмент" имеет остаток 4 номера
    Когда наступает релиз-дата
    Тогда остаток не возвращается и фиксируется в обязательстве выкупа

  Сценарий: Настройка порога уведомлений
    Когда менеджер задаёт порог sell-through 70 % для своих объектов
    Тогда уведомления формируются по порогу 70 %
```

## US-07. Мониторинг и повторная публикация

> **Как** администратор системы, **я хочу** видеть статус публикации по каналам, инциденты и иметь возможность повторить публикацию, **чтобы** быстро устранять сбои синхронизации и не допускать продаж по устаревшим данным.

**Приоритет:** Must. **Связи:** BG-2, BG-3, BG-7; BR-13, BR-14; EXC-1; C-07, C-11.

**Acceptance Criteria**

```gherkin
# language: ru
Функция: Мониторинг публикации и инциденты

  Сценарий: Автоматические повторы при сбое канала
    Дано канал "OTA-1" возвращает ошибку 503
    Когда система публикует изменение
    Тогда выполняются повторы через 1, 2, 4 и 8 минут
    И каждый повтор использует тот же "Idempotency-Key"

  Сценарий: Включение fail-safe
    Дано изменение не доставлено в канал "OTA-1" в течение 15 минут
    Тогда система закрывает продажи в канале "OTA-1"
    И создаёт инцидент и уведомляет администратора
    И статус канала "Ошибка синхронизации"

  Сценарий: Ручная повторная публикация
    Дано инцидент по каналу "OTA-1" открыт
    Когда администратор устраняет причину и нажимает "Повторить публикацию"
    Тогда система повторно отправляет изменения
    И после ACK выполняет сверку остатков и снимает fail-safe
    И инцидент закрывается с записью в журнале

  Сценарий: Обнаружение расхождения при сверке
    Когда сверка остатков выявляет расхождение в канале
    Тогда создаётся инцидент с указанием даты, категории и величины расхождения
    И эталонные значения платформы отправляются в канал повторно

  Сценарий: Доступ только для уполномоченной роли
    Когда пользователь без роли "Администратор" открывает панель инцидентов
    Тогда система возвращает "403 Forbidden"
```

## US-08. Обновление по API

> **Как** отельер, использующий PMS или channel manager, **я хочу** передавать квоты, цены и ограничения по API, **чтобы** исключить двойной ввод и ошибки рассинхронизации между моей системой и туроператором.

**Приоритет:** Should. **Связи:** BG-1, BG-6, BG-7; ALT-3; BR-03...BR-09; C-02, C-08, C-09.

**Acceptance Criteria**

```gherkin
# language: ru
Функция: Интеграция по API

  Сценарий: Успешная передача пакета
    Дано channel manager отельера авторизован по токену
    Когда он отправляет пакет из 300 строк "дата × категория × тариф" с заголовком "Idempotency-Key"
    Тогда система возвращает 202 Accepted и идентификатор пакета
    И результат по каждой строке доступен по идентификатору пакета

  Сценарий: Повторная отправка того же пакета
    Когда channel manager повторно отправляет пакет с тем же "Idempotency-Key"
    Тогда система возвращает результат первой обработки
    И повторного изменения данных не происходит

  Сценарий: Частично некорректный пакет
    Дано в пакете 300 строк, из них 5 нарушают правила "BR-06"
    Когда система обрабатывает пакет
    Тогда 295 корректных строк применены
    И 5 строк отклонены с кодами ошибок в формате "application/problem+json"

  Сценарий: Превышение размера пакета
    Когда пакет содержит более 10000 строк
    Тогда система возвращает "413 Payload Too Large"

  Сценарий: Превышение частоты запросов
    Когда channel manager отправляет более 60 запросов в минуту на один объект
    Тогда система возвращает "429 Too Many Requests" с заголовком "Retry-After"

  Сценарий: Неавторизованный доступ
    Когда запрос отправлен без токена или по протоколу HTTP
    Тогда система отклоняет запрос ("401 Unauthorized" или отказ в соединении)
```
